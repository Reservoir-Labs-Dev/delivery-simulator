# ARCH-004: Data Model

**Status:** Living document — update when migrations are generated during implementation
**Last updated:** 2026-05-04

---

## 1. Overview

Each service owns its own PostgreSQL schema. No cross-schema foreign keys exist. This document defines every table in every schema, including column types, constraints, and indexes. The SQL here is the design target — EF Core migrations are the authoritative runtime source once implementation begins. If a migration diverges from this document, update this document.

All tables use `uuid` primary keys generated by the application (not `SERIAL`). All timestamps are `timestamptz` (UTC).

---

## 2. Schema: `orders` (OrderService)

### `orders.orders`

Persists every order accepted via `POST /orders`. This is the system of record for order identity and initial state.

```sql
CREATE TABLE orders.orders (
    id                  UUID            PRIMARY KEY,
    customer_id         TEXT            NOT NULL,
    status              TEXT            NOT NULL,   -- enum: see below
    total_amount_cents  INT             NOT NULL CHECK (total_amount_cents > 0),
    currency            TEXT            NOT NULL DEFAULT 'USD',
    created_at          TIMESTAMPTZ     NOT NULL DEFAULT now(),
    updated_at          TIMESTAMPTZ     NOT NULL DEFAULT now()
);

CREATE INDEX idx_orders_customer_id  ON orders.orders (customer_id);
CREATE INDEX idx_orders_status       ON orders.orders (status);
CREATE INDEX idx_orders_created_at   ON orders.orders (created_at DESC);
```

Valid `status` values (mirrors `OrderStatusChangedNotification.Status` from ARCH-002):

```
CREATED | PAYMENT_PROCESSING | PAYMENT_SUCCEEDED | PAYMENT_FAILED |
KITCHEN_PREPARING | ORDER_READY |
DELIVERY_IN_PROGRESS | DELIVERED | DELIVERY_FAILED | DEAD_LETTERED
```

### `orders.order_items`

Line items belonging to an order. Child of `orders.orders`.

```sql
CREATE TABLE orders.order_items (
    id              UUID    PRIMARY KEY,
    order_id        UUID    NOT NULL REFERENCES orders.orders(id),
    item_id         TEXT    NOT NULL,
    name            TEXT    NOT NULL,
    quantity        INT     NOT NULL CHECK (quantity >= 1),
    unit_price_cents INT    NOT NULL CHECK (unit_price_cents >= 0)
);

CREATE INDEX idx_order_items_order_id ON orders.order_items (order_id);
```

### `orders.processed_event_ids`

Idempotency table. OrderService does not consume RabbitMQ events in the happy path (it only publishes), but it does consume `OrderStatusChanged` signals to update `orders.status`. This table deduplicates those updates.

```sql
CREATE TABLE orders.processed_event_ids (
    event_id        UUID        PRIMARY KEY,
    processed_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

## 3. Schema: `payments` (PaymentService)

### `payments.payment_records`

One row per payment attempt outcome. Multiple rows can exist for the same `order_id` if retries occurred.

```sql
CREATE TABLE payments.payment_records (
    id                  UUID        PRIMARY KEY,
    order_id            UUID        NOT NULL,
    status              TEXT        NOT NULL,  -- SUCCEEDED | FAILED
    amount_charged_cents INT        NOT NULL,
    currency            TEXT        NOT NULL DEFAULT 'USD',
    attempt_number      INT         NOT NULL DEFAULT 1,
    failure_reason      TEXT,                 -- NULL if succeeded
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_payments_order_id    ON payments.payment_records (order_id);
CREATE INDEX idx_payments_status      ON payments.payment_records (status);
CREATE INDEX idx_payments_created_at  ON payments.payment_records (created_at DESC);
```

### `payments.processed_event_ids`

Deduplicates `order.created` messages redelivered by RabbitMQ.

```sql
CREATE TABLE payments.processed_event_ids (
    event_id        UUID        PRIMARY KEY,
    processed_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

## 4. Schema: `kitchen` (KitchenService)

### `kitchen.kitchen_orders`

Tracks preparation state for each order. One row per order (not per attempt — preparation is not retried at the kitchen level once started).

```sql
CREATE TABLE kitchen.kitchen_orders (
    id              UUID        PRIMARY KEY,
    order_id        UUID        NOT NULL UNIQUE,
    status          TEXT        NOT NULL,  -- PREPARING | READY
    prep_started_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    prep_ready_at   TIMESTAMPTZ,           -- NULL until READY
    prep_duration_ms INT                   -- NULL until READY
);

CREATE INDEX idx_kitchen_orders_order_id   ON kitchen.kitchen_orders (order_id);
CREATE INDEX idx_kitchen_orders_status     ON kitchen.kitchen_orders (status);
```

### `kitchen.processed_event_ids`

Deduplicates `payment.succeeded` messages.

```sql
CREATE TABLE kitchen.processed_event_ids (
    event_id        UUID        PRIMARY KEY,
    processed_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

## 5. Schema: `delivery` (DeliveryService)

### `delivery.deliveries`

One row per delivery attempt. Multiple rows can exist for the same `order_id` under chaos scenario 2 (delivery failure loop).

```sql
CREATE TABLE delivery.deliveries (
    id              UUID        PRIMARY KEY,
    order_id        UUID        NOT NULL,
    status          TEXT        NOT NULL,  -- IN_PROGRESS | COMPLETED | FAILED
    attempt_number  INT         NOT NULL DEFAULT 1,
    failure_reason  TEXT,                  -- NULL if completed
    started_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    completed_at    TIMESTAMPTZ            -- NULL until terminal state
);

CREATE INDEX idx_deliveries_order_id    ON delivery.deliveries (order_id);
CREATE INDEX idx_deliveries_status      ON delivery.deliveries (status);
CREATE INDEX idx_deliveries_started_at  ON delivery.deliveries (started_at DESC);
```

### `delivery.processed_event_ids`

Deduplicates `order.ready` messages.

```sql
CREATE TABLE delivery.processed_event_ids (
    event_id        UUID        PRIMARY KEY,
```

## 6. Schema: `metrics` (shared — written by all services)

All four services write to a shared `metrics` schema for experiment data collection (DOG-51). This is the one exception to the no-cross-schema rule — the metrics table is append-only and write-only from each service's perspective. No service reads from it during normal operation.

### `metrics.events`

One row per domain event processed by any service. Used to compute throughput, latency, retry rates, and DLQ rates across experiments.

```sql
CREATE SCHEMA IF NOT EXISTS metrics;

CREATE TABLE metrics.events (
    id              UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
    experiment_id   TEXT        NOT NULL,  -- e.g. 'exp-1-happy-path'
    order_id        UUID        NOT NULL,
    event_type      TEXT        NOT NULL,  -- routing key, e.g. 'order.created'
    source_service  TEXT        NOT NULL,
    outcome         TEXT        NOT NULL,  -- PROCESSED | RETRIED | DEAD_LETTERED | SKIPPED
    attempt_number  INT         NOT NULL DEFAULT 1,
    processing_ms   INT,                   -- handler duration in milliseconds
    chaos_scenario  TEXT,                  -- NULL if no chaos active
    recorded_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_metrics_experiment_id  ON metrics.events (experiment_id);
CREATE INDEX idx_metrics_order_id       ON metrics.events (order_id);
CREATE INDEX idx_metrics_event_type     ON metrics.events (event_type);
CREATE INDEX idx_metrics_recorded_at    ON metrics.events (recorded_at DESC);
```

## 7. EF Core mapping notes

### Schema scoping

Each service's `DbContext` sets its schema in `OnModelCreating`:

```csharp
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.HasDefaultSchema("orders"); // or payments / kitchen / delivery
}
```

### UUID generation

PKs are generated in application code using `Guid.NewGuid()`, not by the database. EF Core configuration:

```csharp
entity.HasKey(e => e.Id);
entity.Property(e => e.Id).ValueGeneratedNever();
```

### Timestamps

All `TIMESTAMPTZ` columns map to `DateTimeOffset` in C#. Configure Npgsql to use `DateTimeOffset` globally:

```csharp
AppContext.SetSwitch("Npgsql.EnableLegacyTimestampBehavior", false);
```

### Enum-as-string

`status` and `outcome` columns are stored as `TEXT` rather than PostgreSQL enums. This avoids migration pain when adding new status values — a new string value requires no DDL change. EF Core stores the C# enum's `.ToString()` value by default with `.HasConversion<string>()`.

### Migrations per service

Each service has its own migration history in its own schema. Run migrations per service:

```bash
dotnet ef migrations add <Name> --project services/order
dotnet ef database update        --project services/order
```

There is no shared migration runner. Each service calls `await db.Database.MigrateAsync()` on startup before the consumer begins processing.

## 8. Idempotency check pattern

Every consumer uses the same pattern against its own `processed_event_ids` table:

```csharp
await using var scope = scopeFactory.CreateAsyncScope();
var db = scope.ServiceProvider.GetRequiredService<TDbContext>();

var alreadyProcessed = await db.ProcessedEventIds
    .AnyAsync(e => e.EventId == eventId, ct);

if (alreadyProcessed)
{
    logger.LogInformation("Skipping duplicate event {EventId}", eventId);
    channel.BasicAck(deliveryTag, multiple: false);
    return;
}

// ... handle the event ...

db.ProcessedEventIds.Add(new ProcessedEventId { EventId = eventId });
await db.SaveChangesAsync(ct);
channel.BasicAck(deliveryTag, multiple: false);
```

The insert and the domain state update should be wrapped in a single `SaveChangesAsync` call (one transaction) to prevent a scenario where the domain update succeeds but the event ID is not recorded, causing the message to be reprocessed on redelivery.
